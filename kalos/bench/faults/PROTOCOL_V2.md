# Planted-fault catalogue v2: pre-registered protocol

Committed on 2026-11-20, in a commit of its own, **before any v2 detector exists
and before the first scored v2 run**. The machine-readable half is
`catalogue_v2.py` (same commit). The truth key `truth_v2.json` and the case-file
hashes `manifest_v2.json` are committed with the case builder, before any
scoring. Nothing in these files may change after the first scored v2 run except
through a dated entry under "Amendments" at the end of this file.

The v1 protocol (`PROTOCOL.md`, `catalogue.py`) is frozen and is not changed by
v2. v1 keeps its own cases, baseline and CI gate.

Seed: `SUITE_SEED_V2 = 20261120`. Protocol version: `"2"`.

## 1. Question

How often does the engine catch the data faults that scientists actually make
in plate screens, clone flasks and scale-up sheets (censored results written as
numbers, missing context, failed controls, mismatched keys, derived and leaked
columns), and how often does it raise an alarm on clean sheets with the same
structure? v2 measures the engine as it is at each commit. It does not fix it.
The WS-C detectors (`kalos/validation/{censoring,leaks,controls,regimes,derived}.py`,
the unit vocabulary) are scored against it.

## 2. Inputs (clean bases)

Every v2 base is generated by `bases_v2.py` from a fixed seed, or derived from a
sheet in `examples/`. No file from outside the repo is read, so every v2 case is
available in CI and none is ever skipped. The bases are synthetic benchmark
fixtures: their outcomes are computed, not measured.

| Base | Source | What it is |
|---|---|---|
| `plate368` | generated | A two-round media screen in 96-deep-well plates: 2 campaigns (`C1`, `C2`) x 2 plates (`P1`-`P4`). Each campaign is an 88-recipe Latin hypercube over pH, glucose, glutamine, feed and osmolality, plus a two-level basal medium. Every recipe sits in one well on each plate of its campaign (replicates on different plates, wells assigned at random). Each plate carries 4 reference-recipe control wells at interior positions. Columns: `run_id, campaign, plate, well, sample_type, recipe_id, medium_base, pH_initial, glucose_gL, glutamine_mM, feed_pct, osmolality_mOsm, notes, titer_g_L`. Titer follows a smooth response (shape as in `examples/synthetic_bioprocess/make_synthetic.py`) with an 8 % well-to-well CV and a 3 % plate-to-plate CV. Range about 0.6-1.9 g/L, so nothing is near the assay limit. About 8 % of rows carry a benign note. |
| `plate368_derived` | `plate368` | plus `glucose_mM = glucose_gL / 180.156 x 1000`, rounded to 2 decimals (consistent on every row) |
| `clone64` | generated | A shake-flask clone comparison: 16 clones x 2 flask media (crossed) x duplicate flasks. Columns: `run_id, clone, flask_medium, seed_vcd_e6_per_mL` (as-run seeding density), `titer_96dwp_g_L` (the previous-stage readout), `titer_g_L`. Five clones lost expression in flasks: their flasks are written `<0.05`, a correctly labelled value below the assay's quantitation limit (0.05 g/L). |
| `scaleup_feed90` | `examples/synthetic_scaleup/synthetic_scaleup.csv` | the 90-row 1-5,000 L ladder, unchanged, plus `feed_pct` (bolus feed as % v/v of the starting volume, uniform 10-30 %, seeded; it has no effect on titer in this base) |

The assay limit is never written as a column: a declared LOD/LOQ is a setup
input (WS-C PR 2), not part of the sheet.

## 3. Cases and blinding

- 18 faults and 4 clean cases (`catalogue_v2.py`). Every case is a `sheet`
  surface case in both tiers.
- The layout is the v1 layout (`PROTOCOL.md` section 3): `cases/case-NN/sheet.csv`
  (rows shuffled with a seed) and `case.json` (surface, file name, target), the
  truth key `evaluator/truth.json` outside `cases/`, and `manifest.json`. NN
  comes from a seeded permutation of the v2 ids. No fault name, planted row or
  expected outcome appears in a case folder.
- Build: `python -m kalos.bench.faults.cases_v2 OUT`. The build is deterministic.
  Its truth key and manifest must equal the committed `truth_v2.json` and
  `manifest_v2.json` byte for byte (`tests/test_planted_faults_v2.py`).
- The v1 blind runner (`kalos.bench.faults.runner`, `observe_case`) reads v2 case
  folders unchanged. It never opens `evaluator/`, the catalogues or the
  committed truth.

## 4. What the engine is asked

Exactly v1 section 4 for the `sheet` surface: fast tier = `parse_upload` +
`_analyze(preflight_only=True)` + `validate_frame` with the analysis path's
arguments; full tier = `pipeline.compute_upload_analysis` with default settings.
The target column is passed explicitly. No LOD/LOQ, roles or plate map is
declared: the cases measure what the engine does with the sheet alone.

## 5. Scoring rule

Per fault case: caught / noticed / missed exactly as v1 section 5 (`caught_if`
matchers; noticed by a `noticed_if` matcher, a new warning-or-worse signal the
clean parent did not raise, or a warning-or-worse signal naming a planted row;
a crash is missed; `harm_if` is evidence only).

Per clean case: a false alarm if the engine refuses or crashes, or if any **v2
false-alarm detector** fires at warning or worse. Two differences from v1, fixed
here before any run:

1. **Planned codes are false-alarm detectors.** v1 leaves `planned=True`
   matchers out of its false-alarm set, so a newly shipped detector is never
   counted against the clean cases. In v2 every `caught_if` matcher counts,
   planned or not. A planned code cannot fire before it exists; from the first
   commit that emits it, it counts.
2. **v1 catch detectors are also v2 false-alarm detectors.** A v2 clean sheet is
   judged against the whole engine (`catch_detectors_v2()` = v2 matchers + v1
   `catch_detectors()`).

### 5.1 Planned finding codes

Each is a `validation` finding in the data-checks format (`check` = code, with
`column`, `rows` and `severity`), from a new module registered in
`kalos/validation/runner.py`. A finding reports. It never changes a value.

| Code | Module | Fires when |
|---|---|---|
| `censored_zero` | censoring.py | exact zeros in a positive concentration outcome |
| `repeated_constant` | censoring.py | one value repeated in a concentration outcome far beyond what the sheet's resolution makes likely |
| `volume_not_concentration` | units (PR 1) | an input carries an amount (volume added) rather than a concentration |
| `stacked_regimes` | regimes.py | scale or duration spans > 100x and the outcome splits with it |
| `plate_effect` | controls.py | a plate-level offset beyond replicate noise |
| `control_out_of_range` | controls.py | a plate's controls fail acceptance against the other plates' controls |
| `group_key_conflict` | leaks.py | one group key links rows with different recipes or campaigns |
| `well_position_conflict` | plate ingest (WS-E) | duplicate or impossible well positions |
| `derived_column_inconsistent` | derived.py | a column that follows a formula of others breaks it on some rows |
| `run_failure_note` | controls.py | free-text notes record a failed or contaminated run |
| `target_linear_combination` | leaks.py | the target is a linear combination of inputs (R^2 >= 0.999) |
| `label_leak` | leaks.py | one column or the missingness pattern predicts a label at > 0.95 balanced accuracy |
| `id_token_feature` | leaks.py | an input equals a token parsed out of an identifier |
| `confounded_grouping` | regimes.py | a grouping column is nested in a process level |
| `measured_after_outcome` | leaks.py | an input is recorded at or after the outcome |
| `plate_position_effect` | plate layout (WS-F) | a row, column or edge effect on the outcome |

Where an existing engine signal is an honest catch it is also listed in the
catalogue (for example `target_leak` or a `dropped_output` role for a leaked
column, `constant_within_group` for clones nested in a medium,
`result_duplicate_entry` for a pasted value). A code that is not in the
catalogue counts only after an amendment.

### 5.2 Rates

As v1: counts with Wilson 95 % intervals: caught / 18, caught-or-noticed / 18,
false-alarm cases / 4, and per detector. Results are labelled **synthetic planted
faults (catalogue v2)**. They say nothing about real sheets beyond that.

## 6. Expected outcomes (normative)

The `expected` text and `caught_if` matchers in `catalogue_v2.py` say what an
honest engine should do, not what this one does. Misses are expected before the
WS-C detectors land. Each fault names the module and PR that should catch it.

## 7. Runs and acceptance

- **First scored v2 run (baseline):** the fast and full tiers at the main commit
  that contains this pre-registration and feat/data-checks, before any WS-C
  detector. It runs in a bench-only PR that adds v2 scoring to the scorer and
  does not change v1 output (the v1 gate stays byte-identical). The scorecard
  is written under `kalos/bench/faults/results/` with commit, seed, tier and
  library versions.
- **Each WS-C detector PR** reports, against this truth key: v2 recall
  (caught / 18, with interval) before and after; no v1 regression (the v1 CI
  gate); clean-case false alarms on both v1 and v2 clean cases no higher than
  the post-data-checks baseline; goldens byte-identical for sheets without the
  new conditions.
- **Known condition in the v1 bases:** `examples/synthetic_bioprocess` codes its
  non-producers as exact `0.0` (70 of 160 rows). By this protocol that is a
  censored-result condition. A `censored_zero` finding on it is correct
  behaviour, not a false alarm, and it is not a v2 clean case. The goldens of
  sheets built from it may change in the censoring PR. That PR flags the change
  and gives the reason.

## 8. What v2 does not claim

- 18 synthetic faults on 4 generated or example sheets. A catch rate here is not
  a catch rate on real lab sheets.
- One seed per fault. Rates are case counts, not probabilities, and the
  intervals are wide.
- The plate, clone and scale bases are simple on purpose: one assay, no missing
  cells, controls at fixed positions. A detector tuned only to them can still
  fail on messier sheets.
- `unrecorded_harvest_time` can only be caught as a plate offset. The sheet
  cannot show that the cause was harvest time.
